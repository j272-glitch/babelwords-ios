(native Kotlin WebView wrapper around the web app), plus how the Firebase Test Lab
cloud-device test is wired into the CI build.

## 1. How the ad system is wired

The web app (loaded in the WebView) calls into native code through a JavaScript bridge:

- **`AdMobBridge.kt`** — registered as `window.AndroidAdBridge`. Primary ad interface.
  Handles `showInterstitial()`, `showRewarded()`, readiness checks, and emits JS
  callbacks (`onInterstitialClosed`, `onInterstitialFailedToShow`, etc.).
- **`AdPreloadManager.kt`** — singleton that preloads ads on `MainActivity.onCreate()`
  in parallel with the WebView, so an ad is cached and ready the instant it's needed.
- **`AdBridge.kt`** — UMP (consent) flow + fallback ad loader.

**Ad loading priority:** preloaded cached ad (fast path) → bridge-loaded ad (fallback).

**Why ads can "fill but not show":** loading and showing are two separate stages.
An ad can load perfectly (AdMob match rate healthy) yet never reach the screen because
a **pre-show guard** rejected it. Most of the fixes below are about that second stage.

## 2. Ad Fix #1 — The 0-impression bug (activity-resumed flag)

**This was the bug causing 100% of ads to never show in production.**

### Symptom
Ads loaded fine, AdMob match rate was healthy, but **zero impressions**. Every show
attempt was silently rejected with code **`-2` "Activity not resumed."**

### Root cause
`AdMobBridge` has an internal flag `isActivityResumed` (defaults to `false`). The show
path refuses to display an ad unless this flag is `true`. The flag is only flipped `true`
by `MainActivity.onResume()` calling `setActivityResumed(true)`.

But that call was guarded by `if (::adMobBridge.isInitialized)`, and **the bridge is
created inside a deferred `decorView.post { }` block** (an ANR-prevention technique)
that runs **after** the first `onResume`. So at `onResume` time the bridge didn't exist
yet → the call was skipped → the activity never paused/resumed again → the flag stayed
`false` **forever** → every interstitial *and* rewarded show was blocked.

Confirmed from an 8 MB device logcat: the string `"Activity resumed state"` (logged by
`setActivityResumed()`) **never appeared once**, while the OS window dump showed the
activity *was* genuinely focused and resumed. The flag was stale, not the lifecycle.

### The fix — "lifecycle-flag-sync" pattern
Track the resumed state in `MainActivity` **independently of bridge init**, and push it
to the bridge the moment the bridge is created:

```kotlin
// MainActivity field — always reflects true lifecycle state, even before the bridge exists
private var activityResumed = false

// onResume()
activityResumed = true
if (::adMobBridge.isInitialized) adMobBridge.setActivityResumed(true)

// onPause()
activityResumed = false
if (::adMobBridge.isInitialized) adMobBridge.setActivityResumed(false)

// Immediately after `adMobBridge = AdMobBridge(this, webView)` is created:
adMobBridge.setActivityResumed(activityResumed)   // <-- the fix
```

This is correct **regardless** of whether the deferred block runs before or after
`onResume`. Both ad types read the same flag, so one fix covers both.

### Verified
On the v36 cloud-device test: `Activity resumed state: true` now logs at startup, there
are **zero** `-2` rejections, and a real
`★★★ PRELOADED INTERSTITIAL IMPRESSION #1 ★★★` rendered on screen.

> **Durable lesson:** Any lifecycle/foreground flag that gates ad shows but lives in a
> bridge created via deferred `decorView.post` **cannot** rely solely on `onResume` to
> seed it. Seed bridge lifecycle flags at **creation time** from independently-tracked
> Activity state. (The `isAppInForeground` flag dodged this bug only because it defaults
> to `true`.)

## 3. Ad Fix #2 — Guaranteed failure callbacks (no hung Promises)

### Problem
The web app shows ads via Promises: it calls `showInterstitial()` and waits for either
`onInterstitialClosed` (success) or `onInterstitialFailedToShow` (failure). If a native
guard rejects the show but **forgets to emit a callback**, the web Promise hangs forever
— the user sees a frozen "loading ad" state and the app looks broken.

### Rule (must hold for every guard)
**Every `show*Ad` guard, and every show-triggered load abort, MUST emit
`onInterstitialFailedToShow` / `onRewardedFailedToShow`.** No silent early returns.

> Note: `emitDirectCallback` can still be dropped if the WebView is detached at that
> instant, so callbacks are best-effort but must always be *attempted*.

## 4. Ad Fix #3 — The `isShowingAd` stuck-flag + watchdog

### Problem
`isShowingAd` is set `true` **before** calling `.show()` to prevent showing two ads at
once. But if `.show()` throws, or stalls with no SDK callback, the flag is stranded
`true` — and then **all** future shows are blocked with code `-4` ("Already showing").

### Fix
- Every `.show()` is wrapped in `try/catch`.
- A **show watchdog** (`SHOW_WATCHDOG_MS = 10000`) arms immediately before `.show()`.
  - If `.show()` throws → reset flag, emit failure (code `-13`).
  - If `.show()` stalls past the timeout → watchdog fires, resets flag, emits failure
    (code `-12`).

> **Diagnostic tip:** the watchdog arms *right before* `.show()`. So if a test runs for
> minutes after a show attempt and the watchdog **never** fires, `.show()` was never
> reached — a *pre-show guard* returned early (this is exactly how Fix #1 was isolated).

## 5. Ad Fix #4 — ANR mitigation (manifest flags)

To stop "Input dispatching timed out" / `nativePollOnce` ANRs caused by the Mobile Ads
SDK doing work on the main thread, two official AdMob flags are set in
`AndroidManifest.xml`:

```xml
<meta-data android:name="com.google.android.gms.ads.flag.OPTIMIZE_INITIALIZATION"
           android:value="true"/>
<meta-data android:name="com.google.android.gms.ads.flag.OPTIMIZE_AD_LOADING"
           android:value="true"/>
```

These move SDK initialization and ad loading off the main thread. **No web-side changes
are needed.**

## 6. Ad Fix #5 — Kotlin / play-services-ads coupling

`play-services-ads` 24.x ships **Kotlin 2.x metadata**, so the project **must** compile
with Kotlin ≥ 2.x. The project is on **Kotlin 2.2.0**. Stay on ads 24.x while
`compileSdk = 35`. Downgrading Kotlin below 2.x will break the ads dependency.

## 7. Ad Fix #6 — Play Console "AD_ID missing" is operational

If the Play Console reports the Advertising ID permission as "missing," this is an
**operational** issue (an old active artifact or a stale data-safety declaration), **not**
a manifest bug — the manifest already declares:

```xml
<uses-permission android:name="com.google.android.gms.permission.AD_ID" />
```

**Fix it by:** verifying the *actual* AAB you uploaded, and superseding/removing old
active artifacts in the Play Console. **Never** choose "Release without permission."

---

## 8. Ad Fix #7 — Ad audio routing

Ads must play at full media volume. The app switches audio routing to `MODE_NORMAL`
while an ad is on screen and restores it afterward. This toggle must fire on **every**
edge: ad shown, ad dismissed, **and** ad failed — across both `AdMobBridge` and
`AdPreloadManager`. Missing the "failed" edge leaves audio in the wrong mode.

## 9. The show-path guard reference (error codes)

When a show is rejected, the bridge emits one of these codes to the web app. Knowing them
makes log triage instant:

| Code | Meaning | Guard |
|------|---------|-------|
| `-2` | Activity not resumed | `isActivityResumed` (fixed — see Fix #1) |
| `-3` | App in background | `isAppInForeground` |
| `-4` | Already showing an ad | `isShowingAd` (see Fix #3) |
| `-10` | Activity reference null | activity lost |
| `-11` | Activity finishing/destroyed | lifecycle |
| `-12` | Show stalled (watchdog fired) | SDK never called back |
| `-13` | `show()` threw | exception in show |

Guard order in `showInterstitialAd()` / `showRewardedAd()`:
`-2` → `-3` → `-4` → `-10` → `-11` → stale-ad reload check → `.show()`.

## 10. Firebase Test Lab cloud-device test in CI

Because builds are CI-only (no device/emulator available locally, iPhone-only owner), the
repeatable way to see what ads actually do on a real device is a **gated Firebase Test Lab
Robo test** added to the GitHub Actions workflow
(`.github/workflows/android-sdk-update-v25.yml`). It runs the release APK on a Google
cloud phone, records **video + Logcat**, and uploads them as a downloadable artifact.

### One-time prerequisites (account setup — cannot be done from code)
1. **Blaze billing** must be enabled on the GCP project (`linguavibe-1`). Test Lab's free
   quota is **console-only** — it is **not** available via `gcloud`/CI.
2. Enable **Cloud Testing API** and **Cloud Tool Results API**.
3. Create a service account, grant it the **Editor** role (needs
   `storage.objects.create` to write results), and add two GitHub secrets:
   - `GCP_SA_KEY` — the service-account JSON
   - `GCP_PROJECT_ID` — the project id

### How to run it
The workflow has a manual input **`run_firebase_test`** (default `false`). Trigger the
workflow with that input set to `true`. The job is gated:

```yaml
firebase-test-lab:
  name: Firebase Test Lab (Robo + Logcat + Video)
  needs: build-android-aab
  if: ${{ github.event.inputs.run_firebase_test == 'true' }}
```

### What the job does (step by step)
1. **Download the release APK** artifact (`continue-on-error` — the AAB build is
   unaffected if the APK step was skipped).
2. **Locate APK** — if none found, it skips the test gracefully instead of failing.
3. **Authenticate to Google Cloud** (`google-github-actions/auth@v2` with `GCP_SA_KEY`).
4. **Set up gcloud** (`setup-gcloud@v2`).
5. **Run the Robo test** — auto-launches the app (which triggers the startup
   interstitial), records video:
   ```bash
   gcloud firebase test android run \
     --type robo \
     --app "<release.apk>" \
     --device model=MediumPhone.arm,version=33,locale=en_US,orientation=portrait \
     --timeout 180s \
     --record-video \
     --project "$GCP_PROJECT_ID"
   ```
6. **Pull Logcat + video** from the auto-created results bucket.
7. **Scan Logcat** for the ad-funnel signature and print it in the job log.
8. **Upload artifact** named `firebase-testlab-v<VERSION_NAME>-<VERSION_CODE>`.

### Critical gotchas (already handled — keep them)
- **Don't create a custom results bucket.** Omit `--results-bucket` so Test Lab
  auto-creates a writable `test-lab-*` bucket. Creating one yourself needs Storage Admin
  rights the service account usually lacks and will hard-stop the job. The job parses the
  results path from gcloud's output (`storage/browser/...` → `gs://...`) and copies it
  down with `gsutil -m cp -r`.
- **`upload-artifact@v4` rejects any path containing a colon `:`.** Test Lab names its
  results folder with a timestamp like `2026-06-22_21:12:16...`, so uploading
  `firebase-results/**` **silently fails** ("no files / upload failed"). The fix: copy
  just `logcat`, `video.mp4`, and `firebase-run.log` into a **flat, colon-free**
  `firebase-artifact/` folder and upload **that**.
- **Gate downstream steps on the APK existing** and make the APK download
  `continue-on-error`, because `assembleRelease` can be skipped while the AAB still
  succeeds.

### iPhone-only / no-Blaze alternative
If you don't want to enable Blaze billing: download the release **APK** artifact in Safari,
upload it to the **Firebase console → Test Lab**, run a Robo test with video on the free
**console** quota, and watch the video + read Logcat directly in the browser.

## 11. Reading the results (the ad funnel)

The "Scan Logcat" step prints a funnel so you can diagnose at a glance. Look for these
markers in order:

| Marker | Means |
|--------|-------|
| `LOADED` | Ad cached and ready ✓ |
| `Attempting to show` / `Auto-show` | Show was triggered |
| **Guard rejection** (e.g. `Activity not resumed`, `App in background`, `Already showing`) | Show was blocked before `.show()` — read the code |
| `FailedToShow` + code | The failure surfaced to the web app |
| `Show watchdog fired` | `.show()` stalled |
| `★★★ ... IMPRESSION #1 ★★★` | **Ad actually rendered** ✓ (the win) |

**Healthy run (post-fix) looks like:**
`LOADED` → `Activity resumed state: true` → `Attempting to show` → `IMPRESSION`,
with **no** guard rejections and **no** `-2`.

**Tip:** guard-rejection warnings don't all match the narrow scan grep, so for deep
triage read the **full** `logcat.txt` inside the downloaded artifact, e.g.
`grep -A40 "Attempting to show" logcat.txt`.
